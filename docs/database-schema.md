# Управление схемой SQLite

Обычный запуск `awgram` больше не создаёт и не обновляет таблицы. Бинарник
запускается только при точном совпадении `schema_version`; это исключает
неявное изменение рабочей БД во время systemd restart.

Команды используют `AWGRAM_CONFIG` (по умолчанию
`/etc/awgram/config.toml`) и читают из него только `db_path`:

```bash
awgram --database-path
awgram --schema-status
awgram --check-db
awgram --migrate-db --confirm-schema-change
```

`--schema-status` работает read-only. Код завершения `0` означает точное
совпадение, `3` — требуется явная миграция, остальные ненулевые коды — ошибка
проверки. Отсутствующий файл команда не создаёт.

`--migrate-db` без `--confirm-schema-change` завершается с кодом `64`. Для
существующей схемы команда сначала создаёт SQLite-consistent backup через
`VACUUM INTO`, проверяет его `PRAGMA quick_check` и наличие обязательных таблиц,
а затем применяет каждый migration batch и новый номер версии одной
транзакцией. Копии хранятся рядом с БД в
`backups/schema-migrations/` и автоматически не удаляются.

`--check-db` открывает файл read-only и печатает JSON-отчёт: версию схемы,
`quick_check`, нарушения внешних ключей, доменные аномалии и количество
незавершённых операций. Код `0` означает здоровую БД, `2` — отчёт сформирован,
но найдены проблемы, `1` — сама проверка не выполнена. Команда ничего не
исправляет и не меняет journal mode.

Новая пустая установка вызывает явную migration-команду до первого запуска.
Обычное обновление существующей установки не имеет права автоматически менять
схему: сначала требуется отдельный согласованный release procedure и проверка
восстановления backup.

Откат бинарника после изменения схемы допустим только если старая версия явно
поддерживает новую additive schema. В остальных случаях сервисы останавливают и
восстанавливают проверенную копию до допуска новых пользовательских записей.
