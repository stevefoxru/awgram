# ZPNet 2.0: финальный аудит релиз-кандидата

Дата среза: 2026-11-11. База сравнения: `v1.98.0` (`d753a20`). Аудит
охватывает локальную цепочку A01–A06 и не является разрешением на публикацию,
изменение production или миграцию БД.

## Решение на текущем срезе

**Статус: NO-GO для production, GO для подготовки `2.0.0-rc.1`.**

Кодовые блокеры, найденные аудитом, исправлены локально. Production-выпуск пока
запрещён, потому что ещё нет результатов Linux CI для объединённой ветки,
репетиции на обезличенной свежей копии production-БД и подписанного ручного
smoke-test критических пользовательских сценариев.

Версия остаётся `1.98.0`. Переход на `2.0.0-rc.1`, создание тега, push и запуск
workflow выполняются только после отдельного подтверждения владельца.

## Подтверждённые проблемы и состояние исправлений

| Область | Подтверждённая проблема | Локальное решение | Остаточный риск |
|---|---|---|---|
| Схема БД | Обычный запуск мог неявно изменять схему | A01: точное совпадение версии, отдельная подтверждаемая migration-команда и backup | Миграцию необходимо репетировать на копии реальной БД |
| Диагностика БД | Не было единого read-only допуска | A02: `--schema-status` и `--check-db` | Нужен сохранённый отчёт с production-копии |
| Платежи | Повторное подтверждение пополнения могло повторно зачислить баланс | A03: смена статуса и запись ledger в одной транзакции | Внешний acquiring/webhook требует отдельного интеграционного теста |
| Telegram | Два процесса могли читать одни и те же updates | A04: межпроцессный lock и ограничения systemd | Перед релизом проверить отсутствие второго legacy-процесса/контейнера |
| Интерфейс | Покупка, пополнение и продление теряли понятный следующий шаг | A05: постоянный экран заявки, понятные статусы и CTA | Нужен ручной тест на мобильном Telegram WebView и обычном браузере |
| Обновление | Бинарник заменялся до проверки совместимости с текущей БД | A06: staged `schema-status` и DB Doctor до установки | Installer-тест должен пройти в Linux CI |
| Выпуск | Не было единого локального release gate и формального runbook | A06: release-preflight, backup/health/rollback runbook | Gate ещё не выполнен целиком в Linux с `cargo-deny` и `shellcheck` |

Исторический `CHANGELOG.md` содержит второй заголовок `Unreleased`. Он не
ломает извлечение notes по точному номеру версии, но должен быть очищен отдельной
нефункциональной задачей до формирования финального changelog.

## Совместимость данных

- Общая SQLite-БД для сайта и бота сохраняется.
- Пользователи, платежи, подписки и VPN-ключи не переносятся в новую БД.
- Обычный старт и installer update не имеют права запускать миграцию.
- Новая версия допускается к текущей БД только при `compatible=true` и успешном
  DB Doctor.
- Если для `2.0.0` понадобится новая схема, это отдельное изменение: backup,
  тест восстановления, репетиция migration-команды и отдельное разрешение.
- Откат только бинарника разрешён, пока schema version не менялась. После
  миграции требуется восстановление согласованного pre-release backup.

## Независимые задачи до RC

1. Объединить A01–A06 в одну review-ветку без squash потери границ аудита.
2. Провести code review изменений БД, платежей, runtime lock и installer.
3. Запустить CI и dependency audit; сохранить ссылки на успешные runs.
4. Выполнить ручной release workflow в dry-run режиме и проверить состав,
   архитектуру и SHA-256 артефактов.
5. На изолированной копии production-БД выполнить schema-status, DB Doctor и
   запуск собранного RC; не использовать живые Telegram credentials.
6. Пройти UX-чеклист на мобильном и desktop: первая/повторная покупка,
   продление, получение конфигурации, установка, активная подписка, поддержка и
   переход сайт↔бот.
7. Проверить installer update и автоматический бинарный rollback в disposable
   Linux VM/container.
8. Подготовить changelog `2.0.0-rc.1` и только после review изменить версию.

Задачи 2, 5, 6 и 7 можно выполнять независимо после появления объединённой
ветки. Тег разрешается только после задач 1–8.

## Последовательность RC → stable

1. Отдельное подтверждение на изменение версии до `2.0.0-rc.1`.
2. Review и merge локальной цепочки в release-ветку; push — отдельное действие.
3. Успешные CI, dependency audit и ручная dry-run сборка.
4. Тест RC на копии БД и ограниченной staging-среде без production updates.
5. Подписанный smoke-test и закрытие найденных критичных/высоких дефектов.
6. Отдельное подтверждение тега RC; наблюдение согласованный период.
7. Для stable повторить gate на неизменном исходном commit, изменить только
   версию/changelog и получить отдельное production approval.
8. Перед production: backup, preflight, ручной deploy, health-check и окно
   наблюдения по процедуре из `release-zpnet-2.md`.

## Stop conditions

- несовпадение commit, версии, тега или checksums;
- неуспешный CI, DB Doctor, `quick_check` или schema compatibility;
- два активных poller-процесса;
- отсутствующий или непроверенный backup;
- необходимость неоговорённой migration-команды;
- повторное списание/зачисление, потеря подписки, ключа или конфигурации;
- невозможность выполнить проверенный откат.

При stop condition выпуск прекращается. Исправление оформляется отдельным
commit, после чего все затронутые gates запускаются заново.
